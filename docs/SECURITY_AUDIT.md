# Zen AI — Enterprise Security Audit & Threat Model

**Standard Reference:** OWASP Top 10 (2021) & OWASP Top 10 for LLM Applications (2025)  
**Security Classification:** Highly Confidential  
**Assessment Target:** Zen AI Multi-Agent Platform (Gateway, Services, Frontend, LLM Pipeline)

---

## 1. Security Posture Summary

The initial audit revealed several high-severity security vulnerabilities typical of rapid prototypes: lack of internal service authentication, missing object-level access controls (IDOR), non-idempotent payment verification, insecure developer backdoors, unconstrained file uploads, and absence of input validation.

This document details every vulnerability, its exploitation impact, CVSS 3.1 rating, and the exact remediation required for enterprise compliance.

---

## 2. Vulnerability Catalog

### VULN-001: Insecure Direct Object Reference (IDOR) / BOLA
- **Component:** Chat Service (`backend/services/chat/controllers/chat.controller.js`)
- **Severity:** High (CVSS 8.5 — `CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:N`)
- **Description:** The `getMessages` and `updateConversation` endpoints accept a `conversationId` or `:id` parameter and directly perform database reads/updates without validating that the conversation belongs to the user specified in the headers:
  ```javascript
  // Existing Vulnerable Code:
  export const getMessages = async (req, res) => {
    const messages = await Message.find({ conversationId: req.params.id }).sort({ createdAt: 1 });
    res.json(messages);
  };
  ```
- **Exploitation:** An authenticated attacker can iterate through ObjectId values to read all conversations and proprietary messages generated by any other enterprise user on the platform.
- **Remediation:** Enforce conversation ownership validation before executing message queries:
  ```javascript
  const conversation = await Conversation.findOne({ _id: conversationId, userId });
  if (!conversation) return res.status(403).json({ success: false, message: "Forbidden" });
  ```

### VULN-002: Unauthenticated Internal Service Endpoints
- **Component:** Auth Service (`backend/services/auth/routes/auth.routes.js`)
- **Severity:** Critical (CVSS 9.8 — `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`)
- **Description:** Endpoints `/internal/update-plan` and `/internal/deduct-credits` do not require any session, JWT, or service-to-service cryptographic authentication. If any microservice port is exposed or reachable via SSRF, arbitrary credit amounts and subscription plans can be modified.
- **Remediation:** Implement cluster-level HMAC signature verification (`x-service-signature`) generated from a shared internal secret with timestamp replay prevention (window: 60 seconds).

---

### VULN-003: Race Condition / Non-Idempotent Payment Verification
- **Component:** Billing Service (`backend/services/billing/controllers/billing.controller.js`)
- **Severity:** High (CVSS 8.1 — `CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:H/A:N`)
- **Description:** `verifyPayment` validates the Razorpay signature, updates the payment record to `paid`, and requests the Auth Service to grant credits. If multiple identical requests are issued concurrently before the first completes, or replayed subsequently, the user account is credited multiple times for a single payment.
- **Remediation:** Enforce atomic database state transition with conditional queries:
  ```javascript
  const payment = await Payment.findOneAndUpdate(
    { orderId: razorpay_order_id, status: "created" },
    { status: "paid", paymentId: razorpay_payment_id },
    { new: true }
  );
  if (!payment) return res.status(409).json({ message: "Payment already processed or invalid" });
  ```

### VULN-004: Hardcoded Development Backdoor in Production Auth
- **Component:** Auth Service (`backend/services/auth/controllers/auth.controllers.js`)
- **Severity:** High (CVSS 8.2 — `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:L/A:N`)
- **Description:** The login controller includes a hardcoded bypass:
  ```javascript
  if (token === "mock-user-token") {
    decoded = { uid: "mock-developer-uid", email: "developer@zen.ai", ... };
  }
  ```
- **Exploitation:** If this is present in production, anyone knowing or guessing the token can log in as a developer account and consume API credits or manipulate platform state.
- **Remediation:** Restrict mock bypass exclusively to `NODE_ENV === "development"` or `NODE_ENV === "test"` and require an explicit environment toggle `ALLOW_DEV_MOCK_LOGIN=true`.

---

### VULN-005: Unrestricted File Upload & Potential Path Traversal
- **Component:** Agent Service (`backend/services/agent/config/multer.js` & `pdfRag.agent.js`)
- **Severity:** Medium (CVSS 6.5 — `CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:L/I:L/A:L`)
- **Description:** File uploads are accepted without strict magic-number MIME type verification, strict filename sanitization, or file size limits, allowing potential denial of service or execution of malicious files.
- **Remediation:** Implement Multer with strict memory/disk storage, UUID-based random filenames, 10MB maximum file size limit, and explicit whitelist of allowed MIME types (`application/pdf`, `image/png`, `image/jpeg`, `image/webp`).

---

### VULN-006: Header Spoofing via Direct Service Invocations
- **Component:** API Gateway (`backend/gateway/utils/proxyWithHeaders.js`)
- **Severity:** High (CVSS 7.5 — `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N`)
- **Description:** Downstream microservices trust `x-user-id` forwarded by the Gateway. However, if a client submits their own `x-user-id` header in the HTTP request to an unprotected endpoint, or if downstream services are directly exposed without perimeter isolation, any user identity can be assumed.
- **Remediation:** The Gateway must sanitize and strip any client-supplied `x-user-*` headers before forwarding, and downstream services must verify an internal signing signature.

---

### VULN-007: Prompt Injection & Insecure Output Handling (LLM01 / LLM02)
- **Component:** Agent Multi-Agent Graphs
- **Severity:** Medium (CVSS 6.3)
- **Description:** Prompts from users were directly concatenated into system instructions without delimiters or input sanitization, making system instructions susceptible to adversarial jailbreaks and instruction override.
- **Remediation:** Use structured message schemas (`SystemMessage`, `HumanMessage`), employ XML-style input boundaries (`<user_prompt>...</user_prompt>`), and implement output validation in the `ReviewValidationAgent`.

## 3. Defense-in-Depth Implementation Checklist

- [x] Strict Content Security Policy (CSP) and Helmet headers on all services.
- [x] CORS origin validation restricted to trusted frontend domains.
- [x] Request rate limiting backed by Redis (sliding window).
- [x] Input validation with Zod schemas for all API payloads.
- [x] NoSQL injection mitigation through sanitized query objects.
- [x] Server-side token validation and secure cookie handling (`HttpOnly`, `SameSite=Lax`, `Secure` in production).
- [x] Cryptographic service-to-service signature verification.
- [x] Sandboxed iframe execution for client code artifacts.
- [x] Zero secrets committed to git repositories (`.env` in `.gitignore`).
